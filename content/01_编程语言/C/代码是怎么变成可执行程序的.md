# 代码是怎么变成可执行程序的

写完一个 `.c` 文件，为什么还要“编译”？已经生成了机器码，为什么还要“链接”？写了 `#include <stdio.h>`，`printf` 的实现就进入程序了吗？

把这些问题放进一次实际构建过程里，会更容易理解。

> [!note] 实验环境
> 示例使用 C17 和 GCC，命令主要按 Windows PowerShell 编写，需要事先安装 GCC 并加入 `PATH`。
> Linux 使用相同的 GCC 参数，把最终输出名 `main.exe` 改为 `main`，运行时使用 `./main`。
> 这里讲的是普通桌面 C 程序的构建过程；具体中间文件、启动代码和库格式会随工具链与平台变化。

# 1 先把一个程序跑起来

新建一个练习目录，在其中创建 `main.c`：

```c
#include <stdio.h>

#define BASE 3

int main(void) {
    int total = BASE + 4;
    printf("total = %d\n", total);
    return 0;
}
```

在这个目录打开终端，执行：

```powershell
gcc -std=c17 -Wall -Wextra -Wpedantic main.c -o main.exe
.\main.exe
```

输出：

```text
total = 7
```

这里的 `.c` 是源代码文本，CPU 不会直接把其中的 `printf`、`return` 当作指令执行。工具链需要把程序转换成目标平台的机器码，并组织成可装载的文件。

`gcc` 在这里充当驱动程序：根据输入文件和参数，协调预处理、编译、汇编和链接等步骤。平时只输入一条命令，中间过程就被一起完成了。

# 2 一条构建命令里发生了什么

先用四个阶段建立整体认识：

```mermaid
flowchart LR
    A["main.c：源代码"] -->|预处理| B["main.i：展开后的 C 代码"]
    B -->|编译| C["main.s：汇编代码"]
    C -->|汇编| D["main.o：可重定位目标文件"]
    D -->|链接| E["main.exe：可执行文件"]
    L["启动文件、库等"] --> E
```

| 阶段 | 主要解决的问题 | 本例的输出 |
| --- | --- | --- |
| 预处理 | 要包含哪些内容？宏和条件编译怎样展开？ | `main.i`，文本 |
| 编译 | C 代码的语法和类型是否合法？怎样生成目标平台的指令？ | `main.s`，文本 |
| 汇编 | 怎样把汇编指令编码，并记录数据、符号和待修正的引用？ | `main.o`，二进制 |
| 链接 | 多个目标文件和库怎样组成程序？外部引用由谁提供？ | `main.exe`，二进制 |

平时说“编译项目”，往往指整套构建过程；在这张表里，“编译”专指生成汇编代码的那个阶段。普通构建也不一定会把 `.i`、`.s` 都保存到磁盘。

下面用 GCC 的停止选项逐步观察，参数的正式定义可以查阅 [GCC 输出控制选项](https://gcc.gnu.org/onlinedocs/gcc/Overall-Options.html)。

# 3 预处理：先确定真正参与编译的文本

执行：

```powershell
gcc -std=c17 -E main.c -o main.i
```

`-E` 表示完成预处理后停止。用文本编辑器打开 `main.i`，通常会看到比原文件多得多的内容。

## 3.1 头文件被包含进来了

`#include <stdio.h>` 会让预处理器查找标准输入输出头文件，并处理其中的内容；它还可能继续包含其他头文件。

因此，结果不是只有原来那几行代码。可以把这个过程理解为“在包含位置展开文件内容”，但展开时还会处理头文件内部的宏、条件编译和嵌套包含。

`stdio.h` 提供标准 IO 接口所需的声明和定义，例如 `printf`、`fopen` 的声明，`FILE` 类型，以及 `EOF` 等宏。此时我们获得的是使用这些接口所需的信息，**包含头文件本身不等于已经完成库的链接**。

## 3.2 宏被替换了

源文件里写的是：

```c
#define BASE 3
int total = BASE + 4;
```

预处理后的相关语句是：

```c
int total = 3 + 4;
```

可以直接在 PowerShell 中找这行：

```powershell
Select-String -Path main.i -Pattern 'int total'
```

注意，这一步替换的是宏。`3 + 4` 是否进一步折叠成 `7`，属于后续编译处理的事情，不能把宏替换理解为运行程序计算结果。

## 3.3 注释与条件编译也在这里处理

普通预处理输出中，注释通常不会保留；`#if`、`#ifdef` 等决定哪些代码被留下。输出里还可能出现 `#` 开头的行标记，用于记录来源文件和行号。

遇到 `xxx.h: No such file or directory`，应先检查头文件是否存在、包含路径是否正确。

# 4 编译与汇编：从 C 代码到目标文件

## 4.1 编译得到汇编代码

接着处理刚才生成的 `main.i`：

```powershell
gcc -std=c17 -Wall -Wextra -Wpedantic -O0 -S main.i -o main.s
```

`-S` 表示生成汇编代码后停止，`-O0` 表示关闭大多数优化，便于观察。

编译器会分析代码的语法、类型与语义，并经过内部表示、指令选择等处理生成汇编。打开 `main.s`，可以寻找 `main` 附近的指令，观察局部变量、参数传递与函数调用如何表达。

汇编内容取决于 CPU 架构、操作系统、编译器版本和优化选项。即使使用 `-O0`，也不保证每一行 C 都对应固定的几条指令，更不保证完全没有任何简化。

## 4.2 汇编得到目标文件

```powershell
gcc -c main.s -o main.o
```

这次输入已经是汇编文件，驱动程序会按其类型调用汇编器。`-c` 表示生成目标文件，不进行链接。

平时更常见的写法是直接从源代码生成目标文件：

```powershell
gcc -std=c17 -Wall -Wextra -Wpedantic -O0 -c main.c -o main.o
```

这条命令包含了预处理、编译和汇编，所以 **`-c` 并不是“只运行狭义的编译阶段”**。

## 4.3 为什么 `.o` 还不能直接运行

`main.o` 是可重定位目标文件。它通常包含机器指令、数据、符号表和重定位信息；启用相应选项时，也可能包含调试信息。

它记录了本文件提供哪些函数或变量、引用了哪些外部符号，以及哪些位置需要后续处理。已有机器码，不代表已经具备完整程序的布局、入口和依赖信息。

关于节、符号等概念，可对照 [GNU ld 的基础概念说明](https://sourceware.org/binutils/docs/ld/Basic-Script-Concepts.html)。

# 5 链接：把程序需要的部分接起来

执行：

```powershell
gcc main.o -o main.exe
.\main.exe
```

结果仍然是 `total = 7`。

链接器会处理输入目标文件与库中的符号引用，安排输出布局，并处理重定位。GCC 驱动还会按工具链默认配置提供启动文件和标准运行库等输入，因此这个例子没有手动列出全部依赖。

这里要区分两个问题：

- **编译时**：通过声明了解函数的返回值、参数等信息，检查调用是否符合接口。
- **链接时**：为外部符号引用找到可用的定义或相应的动态链接信息。

所以，函数有声明，并不代表实现已经参与构建。

也不能把链接简单理解为“将所有库的完整代码复制进 exe”。程序可能混合使用静态库和动态库，两者在第 8 节继续说明。相关参数见 [GCC 链接选项](https://gcc.gnu.org/onlinedocs/gcc/Link-Options.html)。

# 6 用多文件例子看懂头文件、声明与定义

单文件示例还不容易体现链接的作用。接下来，把加法操作移到单独的源文件。

仍在练习目录中操作：**用下面的代码替换原来的 `main.c`，再新增另外两个文件**。

```text
练习目录/
    main.c
    math_utils.h
    math_utils.c
```

## 6.1 头文件声明接口

`math_utils.h`：

```c
#ifndef DEMO_MATH_UTILS_H
#define DEMO_MATH_UTILS_H

int add(int a, int b);

#endif
```

`int add(int a, int b);` 是函数声明：告诉编译器 `add` 接收两个 `int`，并返回一个 `int`。它没有函数体，不会凭空产生加法的实现。

外面的三条预处理指令构成头文件保护宏：在一次预处理过程中，第一次包含后宏已定义，再次包含时会跳过受保护的内容。

**保护宏解决的是同一个翻译单元内的重复包含问题。** 它不会阻止两个不同的 `.c` 文件各自包含这个头文件。可以查阅 [GCC 头文件保护说明](https://gcc.gnu.org/onlinedocs/cpp/Once-Only-Headers.html)。

## 6.2 源文件提供定义

`math_utils.c`：

```c
#include "math_utils.h"

int add(int a, int b) {
    return a + b;
}
```

带函数体的这部分是定义，提供了函数的具体行为。实现文件也包含自己的头文件，能让编译器检查这里的定义是否与公开声明一致。

`main.c`：

```c
#include <stdio.h>
#include "math_utils.h"

#define BASE 3

int main(void) {
    int total = add(BASE, 4);
    printf("total = %d\n", total);
    return 0;
}
```

`main.c` 使用接口，`math_utils.c` 提供实现，头文件让两边共享同一份接口声明。

## 6.3 分别生成目标文件，再链接

```powershell
gcc -std=c17 -Wall -Wextra -Wpedantic -O0 -c main.c -o main.o
gcc -std=c17 -Wall -Wextra -Wpedantic -O0 -c math_utils.c -o math_utils.o
gcc main.o math_utils.o -o main.exe
.\main.exe
```

预期仍输出 `total = 7`。也可以一次完成：

```powershell
gcc -std=c17 -Wall -Wextra -Wpedantic main.c math_utils.c -o main.exe
```

这里，`main.c` 及其包含的头文件经过预处理后形成一个翻译单元，`math_utils.c` 及其包含内容形成另一个。两者通常独立编译，再通过链接组合。

在这种普通构建方式下，头文件作为包含内容参与编译，不需要把 `.h` 也列进生成 exe 的命令。也不要通过 `#include "math_utils.c"` 来代替正常的多文件构建。

## 6.4 头文件为什么不只是一张“函数清单”

头文件还常放宏、类型定义、结构体和枚举定义，以及外部变量声明，例如：

```c
extern int counter;  /* 声明：对象的定义在别处。 */
```

对应某一个源文件可以提供：

```c
int counter = 0;     /* 定义：为这个对象提供存储。 */
```

对入门项目，通常把需要共享的普通函数声明放进 `.h`，函数定义和外部变量定义放进某一个 `.c`。

这是一种组织规则，不能说成“头文件绝对不能出现函数体”。例如，适当编写的 `static inline` 函数可以定义在头文件中；C++ 模板也有不同的组织需求。

另外，在 GCC 的常见配置下，`#include "math_utils.h"` 会先从当前包含文件所在目录查找；`#include <stdio.h>` 使用配置的包含搜索路径。`-I` 等选项可以改变路径，并不是仅凭引号或尖括号就能判断文件来自哪里。见 [GCC 头文件说明](https://gcc.gnu.org/onlinedocs/cpp/Header-Files.html)和[包含路径说明](https://gcc.gnu.org/onlinedocs/cpp/Search-Path.html)。

# 7 亲眼观察符号与链接错误

如果 GCC 工具链同时提供 GNU `nm`，在多文件例子编译完成后执行：

```powershell
nm main.o
nm math_utils.o
```

在输出中寻找 `add`，关注下面的关系：

```text
main.o：           U add
math_utils.o：     T add
```

这里省略了地址和其他符号。某些平台可能给符号名加前缀，实际输出不必逐字相同。

| 标记 | 在本例中的含义 |
| --- | --- |
| `U` | 这个目标文件引用了该符号，但没有提供定义 |
| `T` | 符号定义在代码节中，这里对应 `add` 的实现 |

这些标记的定义见 [GNU nm 手册](https://sourceware.org/binutils/docs/binutils/nm.html)。`main.o` 里有 `U add` 是正常的：单独生成目标文件时，可以保留等待链接处理的外部引用。

## 7.1 故意漏掉一个目标文件

现在只链接 `main.o`：

```powershell
gcc main.o -o missing_add.exe
```

预期失败，诊断中通常包含 `undefined reference` 和 `add`。因为当前 `main.o` 知道如何调用 `add`，但这条链接命令没有提供它的实现。

补上 `math_utils.o` 才能完成链接。仅把 `math_utils.h` 放在目录里，或者再写一次 `#include`，都解决不了这个问题。

## 7.2 为什么头文件保护宏防不住多重定义

假设把下面这个普通函数定义放进头文件：

```c
int add(int a, int b) {
    return a + b;
}
```

两个不同的 `.c` 都包含它，就可能各自生成一份具有外部链接的 `add` 定义。链接时便出现 `multiple definition` 一类错误。

即使头文件有保护宏，它也只是让内容在各自的翻译单元里展开一次，不能把整个项目限制为一份定义。

# 8 静态库与动态库：实现最终放在哪里

代码多了以后，可以把一组可复用实现组织成库。

| 方式 | 构建时发生什么 | 运行时的特点 |
| --- | --- | --- |
| 静态链接某个库 | 通常从归档中选取需要的目标文件，把相关代码和数据纳入输出 | 通常不需要该库对应的动态库文件，但仍可能依赖其他动态库 |
| 动态链接某个库 | 记录相应的依赖与符号信息，具体形式随平台变化 | 装载或运行时需要可用且兼容的动态库 |

常见文件包括 GCC 工具链的静态归档 `.a`、Windows 动态库 `.dll`、Linux 共享库 `.so`。Windows 下 `.lib` 既可能是静态库，也可能是供链接 DLL 使用的导入库，不能仅看后缀判断。

还可以用当前多文件例子试一次静态归档。需要工具链提供 `ar`：

```powershell
ar rcs libmathutils.a math_utils.o
gcc main.o -L. -lmathutils -o main_from_lib.exe
.\main_from_lib.exe
```

这里把 `math_utils.o` 打包进归档；`-L.` 增加当前目录为库搜索位置，`-lmathutils` 请求链接对应的库。对本例新建的目录，它会找到刚生成的 `libmathutils.a`。

把引用者 `main.o` 放在库参数之前，是使用 GCC/GNU 链接器处理静态归档时应养成的习惯，库的搜索顺序会影响符号解析。

**本例把自定义的加法实现放进静态库，不代表整个程序已经完全静态链接。** C 运行库等依赖仍由工具链配置决定。

# 9 生成可执行文件以后，怎样到达 `main`

构建成功与运行成功是两个阶段。运行程序时，系统还需要识别可执行文件、建立进程地址空间，并装载代码、数据和所需依赖。

对于普通桌面 C 程序，可以先按下面的顺序理解：

```text
启动程序
    ↓
系统装载程序，处理必要的动态库依赖
    ↓
执行运行时启动代码，准备 C 运行环境
    ↓
调用 main
    ↓
main 返回，运行时执行正常退出处理
    ↓
进程结束，返回退出状态
```

这是便于入门的概括，具体装载与初始化步骤会因平台不同而变化。例如，[Microsoft CRT 初始化说明](https://learn.microsoft.com/en-us/cpp/c-runtime-library/crt-initialization?view=msvc-170)介绍了其启动代码初始化运行库、再调用用户 `main` 的过程。

所以，`main` 是普通宿主环境 C 程序的入口函数，但不应理解成操作系统一启动进程就直接执行的第一条机器指令。

在我们的程序中，`return 0;` 表示成功结束；正常从 `main` 返回还会触发正常退出处理，例如刷新和关闭标准 IO 流。

Windows 常见可执行格式为 PE，Linux 常见为 ELF。把文件名改成 `.exe`，不会把另一种格式的文件变成 Windows 程序；可执行文件还受 CPU 架构、ABI 和运行环境约束。

# 10 遇到问题，先判断卡在哪一步

| 现象或常见诊断 | 优先检查的阶段 | 从哪里查起 |
| --- | --- | --- |
| `xxx.h: No such file or directory` | 预处理 | 文件是否存在，名称和包含路径是否正确 |
| 缺分号、类型不兼容、使用未声明的标识符 | 编译 | 对照源代码与声明，先处理第一处有效诊断 |
| `undefined reference to add` | 链接 | 是否编译并链接了提供定义的源文件或库 |
| `multiple definition of add` | 链接 | 是否重复参与构建，或在头文件里放了普通外部定义 |
| 已生成程序，但启动时提示缺少 DLL | 装载或运行 | 依赖是否可用，版本与架构是否匹配 |
| 能启动，但结果错误或访问异常 | 运行 | 程序逻辑、边界、指针、资源与输入条件 |

这些是排查方向，诊断文字和具体边界会随工具链变化；例如类型不兼容可能只是警告，也可能直接成为错误。

> [!summary] 复习时检查这几个问题
> 1. `-E`、`-S`、`-c` 分别停在哪里？
> 2. 头文件提供了声明，为什么仍可能出现未定义引用？
> 3. `.o` 已经有机器码，为什么通常不能直接运行？
> 4. 两个 `.c` 包含同一个头文件，为什么保护宏防不住普通函数的多重定义？
> 5. 使用静态库，是否就意味着整个程序没有动态依赖？
> 6. 执行到 `main` 之前，谁在准备运行环境？

读懂这些后，再回到 C 语言基础里的多文件编程部分，头文件、源文件和链接命令就能对应起来了。
