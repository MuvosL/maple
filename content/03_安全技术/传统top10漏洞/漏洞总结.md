# SQL

---

## 什么是 SQL 注入,SQL注入的防御,实际测试中如何测试sql注入，如何找sql注入,常用的绕过手段和思路

SQL 注入就是用户输入没被过滤，直接拼到数据库查询语句里，攻击者能构造特殊字符把原本的 SQL 逻辑改掉，实现脱库、删库、越权查数据；防御核心就几点，最稳的是用预编译语句（参数化查询），别直接字符串拼接，再配合严格的输入过滤、输出编码、最小权限原则，后台数据库权限别给太高，再加上 WAF 和安全函数辅助；实际测试里我一般先找跟数据库交互的点，比如登录框、搜索、查询参数、ID 传参、手机号、用户名这些地方，先单引号、and 1=1、and 1=2 看页面或返回包有没有差异，再试 order by 判断字段数，用 union 查库名表名字段，看是否有报错、延时、布尔盲注迹象；防御常见坑就是只前端过滤、只过滤特殊字符没做预编译、黑名单不全、过滤函数可绕过、权限给太大、日志没开；绕过思路就是针对 WAF 和过滤规则来，比如大小写混写、内联注释、编码绕过、替换关键字、用等价函数替换，比如 and 换成 &&，or 换成 ||，空格换成 /**/、% a0、括号等，再结合延时、报错、盲注的姿势去绕。

---

## 预编译和参数化查询说一说，如何写，写了就安全了嘛

预编译和参数化查询其实是一回事，核心就是把 SQL 语句的**结构**和**用户输入的数据**彻底分开，先把固定的 SQL 逻辑发给数据库编译好，再把用户传的参数当纯数据传进去，不会被当成 SQL 指令执行；写的时候很简单，比如 Java 用 PreparedStatement，PHP 用 PDO，把变量的地方用？或者命名占位符代替，绝对不直接把用户输入拼到 SQL 字符串里；但写了也不是 100% 安全，比如**预编译用错**、把参数又拿去拼接 SQL、**order by/group by/limit/in 这些动态排序、分页、列表场景没法用参数化**，如果直接拼用户输入照样能注入，还有**二次注入**这种，数据存库时看着干净，后面被业务代码取出来拼接 SQL 也会出问题，另外数据库权限过大、WAF 没开、日志不全也会放大风险，所以参数化是核心，但必须配合输入校验、最小权限、业务逻辑安全才能真正防住。

---

## 报错注入函数有哪些，一般会怎么用

常用的就那几个高频函数，MySQL 里最核心的就updatexml、extractvalue、floor这三个，别的基本很少用，用法很固定，都是套固定 payload，把要查的 SQL 语句嵌进去，页面会把查询结果当成报错信息吐出来，比如查库名、表名、字段、数据都能用，updatexml 和 extractvalue 用法几乎一样，就是把查询语句放在中间的参数位置，格式都是固定的，直接套就行，比如 updatexml (1,concat (0x7e,(select database ()),0x7e),1)，页面就会直接爆出当前数据库名，extractvalue 换个函数名格式一样，floor 是利用 count 和 rand 冲突报错，适合前两个被过滤的情况，一般用 select count (*) from information_schema.tables group by concat ((查询语句),floor (rand (0)*2))，实际测试时直接把想查的 SQL 替换进去就行，不用改别的结构，遇到 WAF 过滤就换函数、加注释、编码绕过，这三个是最稳、最常用、面试必说的报错注入函数。

---

## 联合注入绕过

只要使用在url内包含union select 的关键字段，就会被拦截

**union #a**

**select 1,2,3# #号表示注释掉后面的内容**

%23为#号，%0a为换行符，所以，绕过的写法如下：

**?id=-1%20union%20%23a%0aselect 1,2,3#**

## SQL 注入和盲注有什么区别？盲注你一般怎么测？

普通注入有回显，可以直接通过报错、联合查询把数据查出来；盲注是**没有回显、没有报错**，看不到数据，只能靠间接判断。

盲注我一般分两种：

- **布尔盲注**：通过页面返回内容的不同，判断条件是否成立，从而一位位猜数据。
- **时间盲注**：页面完全没变化，就用 `<font style="color:#DF2A3F;background-color:rgba(0, 0, 0, 0);">sleep()</font>` 让数据库延迟，根据**响应时间长短**来判断条件是否正确。

简单说：普通注入靠 “看”，盲注靠 “猜” 和 “等时间”。

## MySQL 里，盲注常用的几个函数你用过哪些？

盲注里我最常用的有这几个：

- **sleep()**：时间盲注，用来延迟判断；
- **substr() / substring()**：一位一位截取字符猜数据；
- **ascii() / ord()**：把字符转成 ASCII 码，方便布尔判断；
- **length()**：先猜长度，再猜内容；
- **if()**：条件判断，成立执行 sleep，不成立就正常。

# XSS

### 1. XSS 是什么

XSS 就是跨站脚本攻击，攻击者在网页里插入恶意 JS 代码，让其他用户访问时自动执行，用来偷 Cookie、劫持会话、钓鱼、篡改页面、获取用户信息，属于前端最常见、危害范围很广的漏洞。

---

### 2. XSS 分哪三类，区别是什么

- 反射型 XSS：恶意代码放在 URL 里，点链接就触发，不存数据库，一次性，常见于搜索框、跳转、参数回显。
- 存储型 XSS：恶意代码上传存到数据库里，别人访问页面就触发，不用构造链接，危害最大，常见于留言、昵称、评论、个人资料。
- DOM 型 XSS：不经过后端，直接通过 JS 把参数插入页面结构，后端看不到，只在前端执行，容易被忽略。

---

### 3. 实际测试怎么找 XSS

我一般先找所有**输入输出点**：搜索框、昵称、留言、评论、个人资料、URL 参数、跳转地址、来源页、反馈表单。先输简单测试 payload，比如 `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);"><script>alert(1)</script></font>`、`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);"><img src=x onerror=alert(1)></font>`，看是否能执行；反射型就看参数是否直接在页面回显，存储型就提交后看页面是否加载执行，DOM 型看前端 JS 有没有直接把 location、URL 参数拼进 DOM。

---

# 4. 最常用、最稳的 payload（面试必说）

最简单、最不容易被拦的就是：`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);"><img src=x onerror=alert(document.domain)></font>`或者 SVG、iframe、input 等标签，不用 script 也能执行，绕过率更高。

---

### 5. 常见绕过思路（实战高频）

- 大小写混写：`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);"><Script></font>`、`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);"><Img></font>`
- 拆分关键字、用注释干扰：`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);"><scri/**/pt></font>`
- 换事件：onerror、onload、onmouseover、onfocus
- 伪协议：`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">javascript:alert(1)</font>`
- HTML 实体编码绕过、引号闭合
- 过滤了 script 就用 img/svg/iframe/body 等
- 绕过 WAF：缩短 payload、拆分字符串、URL 编码、Unicode 编码

---

### 6. XSS 能干嘛（真实危害）

- 偷 Cookie 拿到登录态，直接登录别人账号
- 劫持用户会话、改密码、改手机号
- 窃取用户信息、浏览记录、输入内容
- 篡改页面内容、挂钓鱼页面、跳恶意网站
- 结合 CSRF 直接做高危操作存储型 XSS 能全站批量危害，比反射型危险得多。

---

### 7. XSS 防御怎么说最标准、最稳

- 输入校验：对用户输入做过滤，限制特殊字符、标签、事件
- **输出编码**：把 `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">< > " ' &</font>` 转成 HTML 实体，这是最核心
- 使用 CSP 策略，限制资源加载和脚本执行
- Cookie 设置 HttpOnly，防止 JS 读取 Cookie
- 避免危险的 JS 函数：innerHTML、document.write、eval 直接拼接用户数据

---

### 8. 防御常见坑（面试官必挖）

- 只前端过滤，后端不处理
- 只过滤几种标签，没做输出编码
- 编码不完整，只滤一部分字符
- 没开 HttpOnly
- 用了不安全的前端渲染方式，直接把用户数据插入 DOM
- 以为加了个过滤就万事大吉，没做整体防护

---

### 9. 一句话总结（面试收尾）

XSS 是插入恶意脚本在用户浏览器执行，分反射、存储、DOM 三类，测试找输入输出点，用 img 等 payload 验证，绕过靠标签、事件、编码混淆，防御核心是**输出编码 + HttpOnly + CSP**，从源头不让脚本执行。

### 1. 问：反射型、存储型、DOM 型，本质区别是什么？

反射型：代码在 URL 里，一次性，不入库，点链接才触发。存储型：代码写进数据库，所有人访问都触发，危害最大。DOM 型：不经过后端渲染，纯前端 JS 把参数插进页面，后端日志看不到。

---

### 2. 问：为什么 `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);"><script>alert(1)</script></font>` 有时候没用？

很多场景过滤了 script 标签，或者页面是异步渲染、动态插入的，script 不会执行。所以实战都用 **img/svg/iframe/body** 这类带事件的，最稳。

---

### 3. 问：你最常用的万能 XSS payload 是哪个？

`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);"><img src=x onerror=alert(document.domain)></font>`这个兼容性最好、绕过率最高，几乎所有场景都能用。

---

### 4. 问：过滤了 `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);"><</font>``<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">></font>` 还能绕吗？

看输出位置：

- 在 HTML 标签里：可以用**事件污染**，比如`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">" onmouseover=alert(1) x="</font>`
- 在 JS 代码里：直接`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">;alert(1);//</font>`闭合语句不一定非要尖括号。

---

### 5. 问：过滤了 `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">onerror</font>` 怎么办？

换事件就行，一堆可以用：`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">onload</font>`、`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">onmouseover</font>`、`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">onmousemove</font>`、`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">onfocus</font>`、`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">onpageshow</font>`、`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">onclick</font>`实在不行用 SVG：`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);"><svg onload=alert(1)></font>`

---

### 6. 问：CSP 开了还能 XSS 吗？

看配置严不严：

- 严格 CSP：禁止内联脚本、只允许信任域名，基本防死。
- 宽松 CSP：`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">unsafe-inline</font>`、`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">unsafe-eval</font>`开着，照样能打。CSP 不是万能，配错等于没配。

---

### 7. 问：HttpOnly 能防 XSS 吗？

只能防**偷 Cookie**，不能防 XSS 本身。弹窗、劫持前端、钓鱼、改接口请求、借用户身份发 CSRF，全都能做。

---

### 8. 问：innerHTML 为什么危险？

不会执行`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);"><script></font>`，但会**渲染标签和事件**：`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">img src=x onerror=alert(1)</font>` 扔进去照样执行。这是前端最容易踩的坑。

---

### 9. 问：什么是 DOM XSS？举个真实场景

就是前端 JS 把 URL 参数直接拼到页面里：`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">var search = location.href.split('q=')[1]</font>``<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">document.getElementById('content').innerHTML = search</font>`后端根本没参与，纯前端造成的 XSS。

---

### 10. 问：WAF 怎么绕？说几个真实思路

- 大小写混写：`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);"><Img OnErRoR=alert(1)></font>`
- 插入注释：`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);"><scri/**/pt></font>`
- 编码绕过：URL 编码、Unicode 编码、HTML 实体
- 换标签：svg、iframe、input、body
- 缩短 payload、拆分字符串、干扰正则

---

### 11. 问：存储型 XSS 为什么比反射型危险？

反射型要诱导点链接；存储型只要**访问页面就自动触发**，可以批量偷 Cookie、劫持全站用户，属于高危漏洞。

---

### 12. 问：XSS 的正确防御顺序是什么？

1. **输出编码**（最核心，转义 < > " ' &）
2. Cookie 设 **HttpOnly**
3. 加 **CSP**
4. 避免危险 JS：innerHTML、document.write、eval
5. 输入做白名单校验，不依赖黑名单

---

### 13. 问：前端过滤了，后端还要做吗？

必须做。前端就是摆设，F12 改代码、抓包改包直接绕。**所有安全逻辑必须在后端做。**

---

### 14. 问：你真实挖 SRC 时，XSS 一般在哪出现？

- 搜索框（反射型最多）
- 昵称、个性签名、留言（存储型高危）
- 商品标题、公告、反馈（存储型）
- 跳转、返回 URL、来源参数（DOM / 反射）
- 后台管理系统的日志、备注字段

# CSRF

---

### 1. CSRF 是什么

CSRF 就是跨站请求伪造，说白了就是攻击者诱导你在已登录的状态下，访问他构造的恶意页面，页面自动向目标网站发请求，因为你浏览器里带着有效 Cookie，服务器就会误以为是你本人操作，从而执行改密码、改手机号、转账这类敏感操作，核心就是利用了浏览器自动带 Cookie 的机制，冒充用户发请求。

---

### 2. CSRF 怎么防御

防御 CSRF 最实用、最通用的方式，就是在敏感操作中加入 CSRF Token 校验，由后端生成唯一随机 Token 存入 Session，前端请求时必须携带该 Token，后端比对一致才允许执行，这是最稳的防护方案；其次要避免使用 GET 请求处理敏感操作，因为 GET 很容易被构造利用，即便改用 POST，攻击者也能通过自动提交表单或 JS 构造 Ajax 发起请求，所以不能只靠请求方法防御；还可以配置 SameSite Cookie，限制 Cookie 只能同站发送，从源头阻断跨站携带；同时可做 Referer/Origin 校验，通过 HTTP 头验证请求来源，但这种方式不够可靠，容易被绕过；最后对修改密码、绑定手机号等高危操作，一定要加上二次身份验证，比如输入旧密码、短信验证码等，进一步降低风险。

---

### 3. 实际测试中怎么测 CSRF

测试很简单，先抓正常的敏感请求，比如改密码、修改资料，去掉 Referer、不带 Token，直接用构造的 HTML 表单或者 Burp 的 CSRF PoC 生成页面，在已登录目标网站的浏览器里打开，看请求能不能直接成功执行，能成功就说明存在 CSRF 漏洞；重点测没有 Token、没有二次验证、只靠 Cookie 鉴权的接口，比如个人信息修改、密码重置、添加管理员这些高危接口。

---

### 4. CSRF 防御常见的坑

最常见的就是**只在 GET 请求防御，POST 请求没做**，或者**Token 写在 Cookie 里，没独立校验**，照样能被利用；还有**Token 固定不变、可预测、可遍历**，等于没防御；只校验 Referer 但没做严格匹配，甚至不校验 Referer；还有关键接口偷懒不加二次验证，只依赖 Cookie 鉴权，这些都是实际项目里最容易出问题的地方。

---

### 5. CSRF 绕过思路

绕过基本就是针对防御措施来，Token 防护就找**Token 泄露、Token 可复用、Token 为空也能通过**的情况；Referer 防护就找**Referer 校验不严、空 Referer 放行、子域名绕过**的漏洞；SameSite 绕过就结合 XSS 漏洞，变成站内请求直接绕过限制；还有一些老旧站点只防御了表单，没防御 JSON / 接口请求，直接构造请求就能绕过。

---

### 6-CSRF 为什么能成功？核心原理是什么？

答：因为浏览器访问某个网站时，会**自动带上对应域名的 Cookie**，而服务端很多时候只靠 Cookie 里的 session 识别登录态，不校验请求是不是用户主动发的。攻击者只要在自己的页面里构造好请求，诱导已登录的用户点开，浏览器就会带着有效 Cookie 帮他把请求发出去，服务端就会当成正常操作执行，这就是 CSRF 的核心。

---

### 7- GET 和 POST 都能做 CSRF 吗？

答：都能。GET 最简单，直接用图片、超链接、iframe 就能发起；POST 可以用自动提交的表单，或者 JS 构造 Ajax 请求，一样能发。很多开发以为只有 GET 有风险，只防护 GET，POST 不做校验，这是最常见的漏洞点。

---

### 8-Token 放在 Cookie 里，能防 CSRF 吗？

答：不能，这是经典错误。Token 存在 Cookie 里，浏览器发起跨站请求时**照样会自动带上**，攻击者根本不需要知道 Token 是什么，请求照样能成功。正确做法是 Token 放在请求头、表单参数里，后端单独校验，不和 Cookie 混在一起。

---

### 4. 问：Referer 校验可以完全防住 CSRF 吗？有什么绕过？

答：不能，只能算辅助。绕过场景很多：比如允许空 Referer，有些浏览器或代理会去掉 Referer，直接就能过；校验规则写得松，只判断是否包含某个字符串，攻击者就能用子域名、路径名绕过；还有一些情况下 Referer 可以被伪造，所以企业里一般只当辅助，不做主防。

---

### 9-SameSite Cookie 怎么防 CSRF？有几种值？

答：SameSite 是用来限制 Cookie 跨站发送的，从源头减少 CSRF 风险。

- `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">Strict</font>`：完全不允许跨站带 Cookie，最安全，但体验差；
- `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">Lax</font>`：大部分跨站情况不带，只有安全的 GET 链接会带，现在浏览器默认；
- `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">None</font>`：必须配合 HTTPS，跨站照样带，等于不防。它能大幅降低风险，但配合 Token 才最稳。

---

### 10- 有了 CSRF Token，为什么还会被绕过？

答：常见几种绕过场景：

- Token 固定不变，所有人都一样；
- 后端不校验 Token，不传也能过；
- Token 从 Cookie 里读取，等于没防；
- Token 会泄露在 URL、日志、页面源码里；
- 只校验首页接口，其他业务接口不校验。只要有一个接口没做，整个系统就存在 CSRF。

---

### 11-CSRF 和 XSS 有什么区别？

答：XSS 是攻击者直接在目标网站上执行脚本，偷 Cookie、操作账号，是**劫持用户本身**；CSRF 是利用用户身份，**冒充用户发请求**，不需要注入代码。XSS 危害更大、能直接打穿，CSRF 只能做用户有权限的操作，比如改密码、加关注、转账。如果一个站有 XSS，那 CSRF 基本可以直接被绕过去。

---

### 12- 哪些接口最容易出 CSRF 漏洞？

答：凡是**只靠登录态就能操作、没有二次验证、没有 Token**的接口都危险：

- 修改密码、修改手机号
- 修改昵称、头像、个人资料
- 添加 / 删除管理员、配置权限
- 下单、支付、转账、提现
- 关注、点赞、评论、删除内容这些都是面试和实战里必测的点。

# SSRF

### 1. SSRF 是什么

SSRF 就是服务端请求伪造，攻击者能让**服务器自己去发起请求**，目标是内网机器、本地服务、云厂商元数据接口。本质就是服务端有个功能（比如获取远程图片、下载文件、网页预览）会去请求用户传的 URL，却没校验目标，导致攻击者可以让服务器去访问它本来能访问、但外部访问不到的地址。

### 2. SSRF 一般出现在哪些功能点

实际测试里我优先看这些地方：

- 头像上传、远程图片抓取、URL 预览
- 后台导入文章、采集内容、PDF 生成
- 发送短信 / 邮件的回调地址
- 代理转发、接口调用、WebHook
- 云主机、容器、内部 API 调用只要是**服务端会去请求用户传入 URL** 的地方，基本都可能出 SSRF。

### 3. 实战中怎么测 SSRF

我一般这么干：

- 先传 `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">http://127.0.0.1:80</font>`、`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">http://localhost</font>` 看能不能访问本地端口
- 再测内网段，比如 `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">192.168.x.x</font>`、`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">10.x.x.x</font>`、`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">172.16.x.x</font>`
- 测云厂商元数据地址，比如 AWS、阿里云、华为云的 metadata 地址
- 用 `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">dict://</font>`、`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">gopher://</font>`、`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">file://</font>` 伪协议读文件、打内网 Redis、MySQL
- 看返回内容：页面标题、报错、响应时间、端口开放状态，都能用来判断漏洞存在只要能让服务器访问到它不该访问的地址，就算 SSRF。

### 4. SSRF 常见防御方式

- 黑名单 / 白名单：**白名单才靠谱**，黑名单很容易绕过
- 限制协议：只允许 `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">http</font>`/`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">https</font>`，禁止 `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">dict</font>`、`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">gopher</font>`、`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">file</font>` 等伪协议
- 禁止访问内网、本地 IP：做 IP 段校验，过滤 127、10、192、172 等内网段
- 限制端口：只开放 80、443、8080 等常用 Web 端口
- 校验域名解析结果，不让域名指向内网 IP
- 加上超时时间、请求次数限制，降低被探测风险

### 5. SSRF 常见绕过思路（面试必说）

- IP 各种变形：`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">127.0.0.1</font>` → `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">127.1</font>`、八进制、十进制、十六进制 IP
- DNS 重绑定：域名解析来回跳公网 / 内网
- 利用 `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">@</font>`、`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">#</font>`、`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">?</font>` 等符号绕过解析
- 短网址、302 跳转、多级跳转绕开校验
- 用 IPv6、特殊域名、子域名绕过
- 绕过端口限制：`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">80</font>` 端口被限制就用 `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">80#</font>`、`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">80?</font>` 等方式
- 利用 `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">[::1]</font>` 访问本地 IPv6

### 6. SSRF 危害

- 扫描内网端口、服务、资产
- 读取云厂商元数据，拿到 AK/SK、临时凭证
- 读取本地文件（file 协议）
- 攻击内网 Redis、MySQL、Fastcgi、Elasticsearch
- 对内网其他机器打漏洞，横向渗透

### 1. 问：SSRF 分哪两种？有什么区别？

答：分**回显 SSRF**和**盲 SSRF**。回显就是服务器会把请求的结果返回给你，能直接看到页面内容、标题、文件内容；盲 SSRF 就是不返回内容，只能靠响应时间、报错、端口是否开放来判断，一般用来扫内网端口。

---

### 2. 问：SSRF 常见的协议有哪些？分别能干什么？

答：实际测试最常用这几个：

- **http/https**：扫内网、读 内网服务 页面
- 场景：内网 tomcat、redis 管理页、jenkins、prometheus
- **file://**：读本地文件，比如 /etc/passwd、C:\Windows\System32\drivers\etc\hosts
- 重点：**不需要开端口，直接读文件**，很多防御会漏掉。
- **dict://**：探测端口、读取 Redis 信息
- 例子：`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">dict://127.0.0.1:6379/info</font>`不用 http 也能打 Redis。
- **gopher://**：最强大， 可以构造任意 TCP 请求，发 POST 包，打 Redis、MySQL、FastCGI、内网服务
- **ftp://**：探测内网 FTP 服务面试官一般只需要记住：**file 读文件，gopher 打内网服务**。
- 面试官一问 “SSRF 最厉害的协议是什么”，你就说：**gopher**。 gopher 最危险，**能把内网几乎所有 TCP 服务都打一遍**，相当于服务器变成你的代理。

---

### 3. 问：云服务器里的 SSRF 最危险的点是什么？

答：最危险的就是**元数据地址**，比如阿里云、AWS、华为云这些，通过 SSRF 访问元数据接口，可以直接拿到**实例角色令牌、AK/SK、临时凭证**，拿到就能控制云服务器、对象存储、甚至整个账号权限，这是 SSRF 里危害最大的场景。

---

### 4. 问：后端只过滤了 127.0.0.1，怎么绕过？

答：绕过方式特别多，随便说几个面试够用：

- 用短域名解析到 127.0.0.1
- IP 进制转换：十进制、八进制、十六进制
- 用 127.1、127.0.1、127.0.0.2 等本地地址
- [::1] IPv6 本地地址
- 302 跳转、DNS 重绑定
- 加端口、加路径、加 @ 符号混淆解析

---

### 5. 问：SSRF 防御，白名单和黑名单哪个靠谱？为什么？

答：**一定是白名单靠谱**。黑名单只能堵已知的内网 IP、协议、关键字，很容易被各种格式绕过；白名单是只允许指定的域名、IP、协议，其他全部拒绝，这才是真正能防住 SSRF 的。

---

### 6. 问：做了 IP 白名单，为什么还可能出 SSRF？

答：常见几个坑：

- 只校验了域名，没校验**域名解析后的 IP**，攻击者用域名指向内网 IP
- 没限制协议，还能使用 file、gopher 等伪协议
- 允许跳转，攻击者构造 302 跳内网
- 白名单不严，比如允许子域名，被构造恶意解析
- IPv6 没做限制，用 [::1] 绕过

---

### 7. 问：SSRF 和 CSRF 有什么区别？

答：简单记：

- **CSRF：是利用用户浏览器，冒充用户去请求目标网站**
- **SSRF：是利用服务器，让服务器去请求内网、本地、云资源**CSRF 是 “借你的身份”，SSRF 是 “借服务器的身份”。

---

### 8. 问：你在实际测试中，一般怎么快速判断 SSRF？

答：我一般三步：

1. 找功能：远程图片、导入 URL、网页预览、WebHook、PDF 生成
2. payload：先测 [http://127.0.0.1:80](http://127.0.0.1:80)，看是否返回本地服务
3. 扩大：再试 file 协议、元数据、内网段、gopher 打 Redis只要服务器能访问到它不该访问的地址，就是 SSRF。

### 问：元数据为什么只能通过 SSRF 访问？

答：因为元数据地址 **只允许本机 / 内网访问**，外网访问不到。只有让服务器替你去请求，才能拿到，这就是 SSRF 的核心价值。

### 问：如果只禁止了 http，还能利用吗？

答：能。还能用 `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">file</font>` 读文件，`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">dict</font>` 打端口，`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">gopher</font>` 打内网，**协议不限制死，SSRF 就防不住**。

### 问：防御 SSRF 只黑名单 IP 行不行？

答：不行，太好绕过了。进制转换、302 跳转、DNS 重绑定、IPv6、短链接、域名指向内网，随便绕。真正安全的是：**白名单域名 / IP + 限制协议 + 禁止跳转 + 解析后校验 IP**。

### 问：SSRF 中，回显与盲 SSRF 区别是什么？

答：

- 回显 SSRF：内容直接返回页面，能读文件、读源码、读元数据；
- 盲 SSRF：不返回内容，只能靠**响应时间、报错、端口 Banner** 判断内网端口开放。

# XXE

### 1. XXE 是什么

XXE 就是 XML 外部实体注入，漏洞出在应用解析 XML 数据的时候，没有禁用外部实体，导致攻击者可以构造恶意 XML，读取服务器本地文件、探测内网端口、发起内网请求，甚至配合其他漏洞 getshell，属于**XML 解析器的配置不安全导致的漏洞**。

---

### 2. XXE 一般出现在哪些地方

凡是用到**XML 格式传参、解析**的地方都可能有：

- 登录、注册接口用 XML 传参
- 文件上传：docx、xlsx、ppt、pdf 这类 Office 文档底层都是 XML
- 支付、回调接口用 XML 交互
- 配置导入、XML 数据提交
- 旧系统、Java 系统、PHP 里用了不安全的 XML 解析器

只要你能提交 XML 给后端解析，就可以测 XXE。

---

### 3. 最简单的 XXE Payload 怎么写（面试必背）

直接构造外部实体，读取本地文件：

xml

```
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE test [
  <!ENTITY xxe SYSTEM "file:///etc/passwd">
]>
<test>&xxe;</test>
```

解析后页面会把 `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">/etc/passwd</font>` 内容直接回显出来，这就是**有回显的 XXE**。

---

### 4. 常见协议和用途

- `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">file://</font>`：读本地文件（最常用）

- Linux：`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">file:///etc/passwd</font>`、`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">file:///proc/self/environ</font>`
- Windows：`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">file://C:/Windows/System32/drivers/etc/hosts</font>`

- `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">http://</font>`：让服务器去请求内网，探测端口、内网服务
- `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">php://filter</font>`：PHP 环境下读文件编码

---

### 5. 什么是盲 XXE，怎么利用

没有回显，不会把文件内容直接返回给你，叫盲 XXE。利用思路：

- 把读取到的内容，通过 **外带通道** 发送到攻击者服务器
- 构造带外网 URL 的实体，把文件内容带到自己的 VPS 日志里
- 或者用 **参数实体 + 外部 DTD** 组合带出数据

---

### 6. 实际测试怎么测 XXE

1. 抓包，看有没有接口是 `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">Content-Type: text/xml</font>` 或纯 XML 提交
2. 把请求体替换成恶意 XXE payload
3. 看是否回显文件内容、是否有解析报错、是否请求了你的外网地址
4. 没回显就试盲 XXE，看能否外带出数据

---

### 7. XXE 常见绕过

- 过滤了 `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">DOCTYPE</font>`：用 `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">ENTITY</font>` 嵌套、换写法
- 过滤了 `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">SYSTEM</font>`：用 `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">PUBLIC</font>` 代替
- 编码绕过：UTF-16 编码、HTML 实体绕过检测
- 限制了协议：用 `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">php://filter</font>`、`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">data://</font>` 等伪协议绕

---

### 8. XXE 防御（最标准、面试满分回答）

核心就一句话：**解析 XML 时，严格禁用外部实体**。具体：

- 禁用 DTD、禁用外部实体、禁用参数实体
- 使用安全的 XML 解析器配置
- 不相信用户提交的 XML，做白名单校验
- 使用更安全的数据格式，比如 JSON，尽量少用 XML

---

### 9. XXE 和 SSRF 有什么关系

XXE 可以**直接触发 SSRF**。用 XML 外部实体写内网地址，服务器解析时就会去请求内网，相当于**用 XML 来打 SSRF**，很多内网探测就是这么来的。

---

### 10. 一句话总结

XXE 是 XML 解析时没禁用外部实体导致的漏洞，能读文件、探内网、打 SSRF，测试就是构造恶意 XML 提交，防御核心是**禁用外部实体 + 安全解析配置**。

### 1. 问：有回显 XXE 和 盲 XXE 到底差在哪？

有回显就是解析完 XML 会把结果直接返回给你，文件内容直接显示在页面或返回包里，一眼就能看到。盲 XXE 就是不返回任何结果，你看不到内容，只能通过**外带数据、响应时间、DNS 请求**来判断是否存在，利用难度更高，但一样能读文件。

---

### 2. 问：盲 XXE 怎么把文件读出来？说具体思路

用**外部 DTD + 参数实体 + 外带通道**，把内容带到自己服务器上。简单说：

1. 构造 XML，引用你外网 VPS 上的恶意 DTD 文件
2. DTD 里把读取的文件内容拼在 URL 上
3. 服务器解析时会去请求你的 VPS，日志里就能看到文件内容这就是**带外（OOB）XXE**，是盲 XXE 最常用的利用方式。

---

### 3. 问：XXE 能读哪些文件？哪些读不到？

能读：

- 文本文件：`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">/etc/passwd</font>`、`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">/etc/hosts</font>`、配置文件、源码
- PHP 能用 `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">php://filter</font>` 读编码后的文件

读不到：

- 二进制文件（图片、数据库文件）会乱码
- 没有权限的文件
- 需要 root 权限的系统关键文件但只要是 Web 进程有权限的文本文件，基本都能读。

---

### 4. 问：XXE 为什么能当 SSRF 用？

因为 XML 外部实体支持 `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">http://</font>` 协议。你写一个内网地址，服务器解析 XML 时就会**主动去请求内网机器**，相当于借服务器的身份探测内网，这就是**XXE 触发 SSRF**。

---

### 5. 问：PHP、Java 哪里容易出 XXE？

- PHP：用了 `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">libxml</font>` 且版本 **<= 2.9.0**，默认**不禁用外部实体**，极易出 XXE。
- Java：很多解析器（如 DocumentBuilder）默认**允许外部实体**，框架没封死就会出。只要开发没手动禁用，基本都有风险。

---

### 6. 问：过滤了 `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">DOCTYPE</font>` 怎么绕？

几种常用绕法：

- 大小写混淆：`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);"><!DocType</font>`
- 编码绕过：UTF-16 编码整个 XML 包
- 用 `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">PUBLIC</font>` 代替 `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">SYSTEM</font>`
- 嵌套、换行、空白符干扰正则很多 WAF 只拦简单的 `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">DOCTYPE</font>`，稍微变形就绕过去了。

---

### 7. 问：为什么有的 XML 上传（如 docx）也会出 XXE？

因为 docx、xlsx、pptx 本质上是**压缩包，里面是 XML 文件**。上传这类文件，后端解析文档内容时，如果没禁用外部实体，就会触发 XXE，这叫**XXE via Office file upload**，实际挖洞非常常见。

---

### 8. 问：XXE 最稳、最标准的防御怎么说？

就这几句，面试满分：

1. **完全禁用外部实体**，这是根上解决
2. 禁用 DTD（文档类型定义）
3. 使用安全的 XML 解析器配置
4. 尽量用 JSON 代替 XML，从格式上规避
5. 不解析用户上传的 Office 文档 XML，或单独做安全处理

---

### 9. 问：XXE 能直接 getshell 吗？

一般不能直接拿 shell，它主要是**读文件、探内网**。但可以：

- 读配置文件拿到数据库账号、密钥
- 读源码拿到其他漏洞
- 读 SSH 密钥、API Key间接 getshell，危害极大。

---

### 10. 问：你实际测试怎么快速判断有没有 XXE？

我一般三步：

1. 找 XML 入口：接口、上传、导入、支付回调
2. 先上最简单 payload：读 `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">/etc/passwd</font>` 或 `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">C:\Windows\boot.ini</font>`
3. 有回显直接出；没回显就上 OOB 盲打，看 VPS 日志有没有请求只要解析器没禁用外部实体，一测一个准。

# 文件上传

### 1. 文件上传漏洞是什么

文件上传就是后端对上传的文件没做安全校验，或者校验能被绕过，攻击者可以直接上传脚本文件（比如 ASP、PHP、JSP、ASPX），拿到网站的后台权限，甚至直接控制服务器，这是 Web 漏洞里危害最大、最直接的一种，上传成功基本等于拿站。

--文件上传通常使用的是HTTP协议，上传的数据格式是multipart/form-data，

---

### 2. 实际测试里一般怎么找、怎么测

先找所有能上传的地方：头像上传、图片上传、附件上传、文章封面、导入文件、证书上传、身份证上传这些，只要能传文件到服务器并且能访问到路径，就可能有漏洞。先正常传一张图片，拿到上传路径和回显地址，再开始尝试绕过，看能不能上传脚本、能不能解析执行。

---

### 3. 最常见的绕过方式（实战高频，面试必说）

- **改文件名绕过**：把 `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">shell.php</font>` 改成 `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">shell.php.jpg</font>`、`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">shell.php;.jpg</font>`、`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">shell%00.jpg</font>`
- **改 Content-Type**：把 `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">application/x-php</font>` 改成 `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">image/jpeg</font>`、`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">image/png</font>`
- **改文件头绕过**：在脚本前面加 `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">GIF89a</font>` 伪造图片头
- **黑名单绕过**：后端只禁了 php，就用 php3、php5、phtml、asp、aspx、jsp、jspx
- **解析漏洞绕过**：IIS 6.0 的 asp 解析、nginx 畸形解析、apache 多后缀解析
- **条件竞争绕过**：文件先上传后删除，在删除之前快速访问让脚本执行
- **二次渲染绕过**：针对图片处理后再保存的场景，在图片里插代码不被渲染掉

---

### 4. 文件上传漏洞的防御（最标准、最稳的答案）

最安全的做法就这几条：

- **文件名随机化**，上传后重命名，不使用用户传的文件名
- **文件后缀白名单**，只允许图片、文档等安全类型，绝对不用黑名单
- **文件内容检测**，校验文件头、文件结构，不是简单读后缀
- **上传目录取消执行权限**，让脚本传上去也运行不了【文件解析漏洞】
- **单独存放上传文件**，放到静态资源服务器或 OSS，不和应用在同一站点
- **限制文件大小、上传频率、文件格式**，防止批量上传木马

---

### 5. 防御里最常见的坑（面试官特别爱问）

- 只在前端校验，后端不校验，F12 改代码就能绕
- 只用黑名单，没禁干净，换个后缀就进去
- 只校验 Content-Type，抓包随便改
- 只校验文件头，不校验内容，图片马能直接插代码
- 上传目录给了执行权限，传上去就能解析
- 没做文件名随机，攻击者能直接猜到路径
- 没做条件竞争防护，导致短时间内可执行

### 2. 问：后端只做了黑名单，怎么绕？

答：绕法特别多，比如：

- PHP：php3、php5、phtml、phps、pHp
- 中间件解析：test.php.jpg、test.jpg.php
- IIS：asp、aspx、cer、cdx
- 大小写、双写、特殊后缀组合，基本都能绕。所以**黑名单基本没用**。

---

### 3. 问：只校验 Content-Type 怎么绕？

答：抓包把 Content-Type 改成 image/jpeg、image/png 就行，后端只认请求头，不认文件真实内容，一抓包就绕。

---

### 4. 问：只校验文件头（比如 GIF89a）怎么绕？

答：在一句话木马前面加个图片头，比如：GIF89a

保存成 php 照样上传解析，这种叫**图片马**。

---

### 5. 问：什么是 %00 截断？什么场景能用？

答：老版本 PHP 特性，把文件名写成 `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">shell.php%00.jpg</font>`，后端会认为是 jpg，保存后变成 `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">shell.php</font>`。现在基本修了，但**老站、CTF 还常考**。

---

### 6. 问：什么是条件竞争？怎么利用？

答：后端是**先上传→再校验→不合法再删除**。我用脚本狂发上传包，同时狂访问路径，在删除之前让脚本执行一遍，就能 getshell。很多开发以为 “先传后删” 安全，其实照样能绕。

---

### 7. 问：Apache 多后缀解析怎么利用？

答：上传 `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">shell.php.xxx</font>`，Apache 从后往前认后缀，不认识 .xxx 就往前看，看到 php 就按 php 解析。

---

### 8. 问：Nginx 解析漏洞怎么利用？

答：上传一张图片马 `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">test.jpg</font>`，访问：`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">test.jpg/.php</font>`Nginx 会当成 php 执行，这是非常经典的中间件解析漏洞。

---

### 9. 问：上传成功但不解析，为什么？

答：一般这几个原因：

- 目录没执行权限
- 上传到了 OSS / 静态资源服务器
- 文件名被改成随机哈希，没有后缀
- 中间件不识别你上传的脚本后缀这种叫**上传成功但无法利用**。

---

### 10. 问：文件上传最稳的防御是什么？

答：就四句话，面试满分：

1. **后缀白名单**，只允许图片等安全类型
2. **文件名随机化**，不使用用户上传的名字
3. **文件内容真实校验**，别只查头
4. **上传目录取消脚本执行权限**，传上去也运行不了

---

### 11. 问：图片二次渲染怎么绕过？

答：就是后端对图片压缩、裁剪、重绘。绕过思路是在**不影响图片结构的地方插代码**，比如 EXIF 信息、图片末尾、图片的注释区，IDAT 块附近，让渲染后还能保留一句话。

---

### 12. 问：上传 .htaccess 有什么用？

答：如果服务器允许上传并解析 .htaccess，可以自己定义解析规则，把 jpg、png 当成 php 执行，等于自己给自己开后门。

# 越权漏洞

### 1. 什么是越权漏洞？

越权就是**越权操作**，简单说：你本来只能看 / 改你自己的数据，结果因为后端没做权限校验，你能看到别人的、甚至能改管理员的数据。这是**业务逻辑漏洞里最常见、最容易被忽略、但危害极大**的一种。

---

### 2. 水平越权 和 垂直越权 有什么区别？（必考）

- **水平越权**：同权限用户之间互相访问。普通用户 → 看 / 改另一个普通用户的数据。
- **垂直越权**：低权限越到高权限。普通用户 → 直接干管理员的事：删用户、改配置、加账号。

一句话记：**水平：同级串门；垂直：小兵造反。**

---

### 3. 实际测试里，越权一般出现在哪里？

凡是带 **用户 ID、订单 ID、文章 ID、参数 ID** 的地方基本都能测：

- 个人资料查看 / 修改
- 订单查看、取消订单
- 查看他人信息、他人文章
- 后台：用户列表、权限配置、日志查看
- 充值、提现、支付、退款
- 所有带 `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">?id=123</font>`、`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">userid=1</font>`、`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">uid=111</font>` 的接口

**只要后端只判断是否登录，不判断 “是不是你的数据”，就一定存在越权。**

---

### 4. 水平越权怎么测？（实战步骤）

1. 登录账号 A，抓包拿到一个查询接口，比如：`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">userinfo?uid=1001</font>`
2. 把 uid 改成别人的 ID，比如 1002、1003
3. 直接发包，如果能看到别人信息 → **水平越权**

修改类更危险：`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">update?uid=1001</font>`直接改别人的资料、手机号、密码。

---

### 5. 垂直越权怎么测？

1. 普通用户登录，抓管理员接口，比如：`<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">admin/user/list</font>`
2. 直接访问，如果能进去 → **垂直越权**
3. 或者把普通用户的请求，去请求管理员功能：删除用户、修改权限、添加管理员

只要**接口没有做角色 / 权限判断**，普通用户就能当管理员用。

---

### 6. 越权最常见的参数有哪些？

面试直接说这些：

- `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">id</font>`
- `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">userid</font>` / `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">uid</font>`
- `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">memberid</font>`
- `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">orderid</font>`
- `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">pid</font>` / `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">parentid</font>`
- `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">adminid</font>`
- `<font style="color:rgb(0, 0, 0);background-color:rgba(0, 0, 0, 0);">roleid</font>`

**只要是能标识 “谁的数据” 的参数，全是越权重灾区。**

---

### 7. 后端最容易犯的错是什么？（高频考点）

只做了两件事：

1. 有没有登录
2. 有没有传参数

**没做第三件最关键的事：判断当前登录用户，是不是这个数据的主人。**

比如：session 里存的 uid=1001请求里带的 uid=1002后端**不比对**，直接执行，越权就出来了。

---

### 8. 越权漏洞的防御怎么说最标准？

1. **所有涉及用户数据的接口，必须从 session 取用户 ID，不能信前端传的 uid**
2. 操作前校验：**当前用户是否有权限操作这条数据**
3. 后台接口必须校验**角色、权限标识**，普通用户不能访问 admin 前缀接口
4. 关键操作（删、改、授权）必须二次校验
5. 接口尽量不要用明文自增 ID，用 UUID、随机串，增加猜测难度

---

### 9. 面试官最爱问的一句话：

**“越权和未授权访问有什么区别？”**

- **未授权访问**：没登录就能用。
- **越权**：登录了，但能访问别人 / 更高权限的功能。

---

### 10. 经典总结

越权是业务逻辑里最常见的漏洞，水平越权是同权限互相访问，垂直越权是低权限越权到管理员，核心原因就是后端**只校验登录、不校验归属与角色**，防御关键就是从会话取用户信息、严格做权限判断，不相信前端传的用户 ID。

# 业务逻辑漏洞

### 1. 任意密码重置

就是通过找回密码功能，**不需要验证身份，直接重置别人账号**。常见原因：

- 只前端校验验证码，后端不校验
- 把用户名 / 手机号放在前端参数里，直接改就能重置别人
- 验证码返回前端、可爆破、可遍历
- token 太简单、可预测、可暴力破解

测试思路：抓重置包，把手机号改成别人的，验证码填对，直接重置。

---

### 2. 验证码漏洞（必考）

面试官最爱问：**验证码有哪些安全问题？**

常见漏洞：

- 验证码**可重复使用**
- 验证码**有效时间太长**
- 验证码**返回前端**（response 里直接有）
- 验证码**可爆破、可遍历**
- 不校验验证码，**前端删了就能过**
- 验证码**太简单**（1234、0000）
- 不限制发送次数 → 短信轰炸

一句话总结：验证码就是用来防批量、防越权、防暴力破解的，**可复用、可爆破、可猜、前端可控，全是漏洞。**

---

### 3. 短信轰炸 / 短信滥用

就是接口**不做频率限制、不做校验**，攻击者可以批量发短信。

出现点：注册、登录、找回密码、绑定手机号、验证码接口。

防御：

- 手机号频率限制（1 分钟 1 条、1 小时 5 条）
- 图片验证码前置验证
- 行为风控
- 黑名单机制

---

### 4. 支付 / 金额 / 订单漏洞

实际面试非常爱问，**逻辑漏洞天花板**。

常见漏洞点：

- 改订单金额：买 100 元商品，抓包改成 0.01
- 改商品数量：改成负数，实现**反向扣费**
- 改订单状态：未支付 → 改成已支付
- 重复提交：支付一次，回调多次，**多次发货 / 多次到账**
- 越权修改别人订单
- 不校验订单归属，直接修改状态

核心一句话：**凡是前端算价格、前端控制支付状态，99% 有漏洞。**

---

### 5. 越权前面讲过，这里补一句高频面试题

**问：水平越权、垂直越权、未授权访问，三者区别？**

- 未授权访问：**没登录就能用**
- 水平越权：**登录了，看 / 改同权限别人的数据**
- 垂直越权：**登录了，普通用户当管理员用**

---

### 6. 业务逻辑漏洞整体测试思路（面试必背）

你就按这个说，非常像真实工程师：

1. 先梳理**完整业务流程**：注册→登录→获取验证码→修改信息→下单→支付
2. 看每一步**前端传了哪些参数**，特别是 ID、手机号、金额、状态
3. 抓包修改关键参数：ID 改别人的、金额改小、状态改已支付、验证码乱填
4. 看后端**是否校验**：是不是只判断登录、不判断归属、不校验金额、不校验验证码
5. 重点看：验证码、密码重置、支付、个人资料、订单、后台权限

逻辑漏洞**不靠工具，靠流程、靠思路、靠业务理解**。

---

### 7. 防御一句话总结（满分回答）

所有关键操作：

- 后端**校验参数合法性**，不信前端
- 校验**用户身份与数据归属**
- 验证码**一次性、时效短、后端校验**
- 金额、订单状态**后端计算，不可篡改**
- 接口加**频率限制、权限校验、二次验证**
